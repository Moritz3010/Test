Taskboard — Technical Architecture

A serverless Kanban app for a 3-person team — no backend server, no containers, no maintenance

Architecture

Browser Chrome / Firefox / Edge — runs the entire app
serves HTML / CSS / JS
Vercel CDN Hosts static files — index.html, style.css, *.js — globally distributed
HTTPS REST API calls (fetch)
Supabase (PostgREST API) Auto-generated REST API — no custom server code needed
SQL queries
PostgreSQL database Managed by Supabase — tables: users, tasks

What Happens When You Open the App

1
Browser requests the page from Vercel
Vercel serves index.html, style.css, and all .js files from its global CDN — no server-side rendering, pure static files.
2
JavaScript boots in the browser
ui.js is the entry point. It checks localStorage for a saved user ID. If none, it shows the nickname picker. If found, it goes straight to the board.
3
Nickname is saved to Supabase
On first visit, the nickname is upserted into the users table via the Supabase API. The returned user ID is stored in localStorage for future visits.
4
Tasks are loaded from Supabase
storage.js calls GET /rest/v1/tasks?select=*,users(nickname) — a single HTTPS request that returns all tasks with their assignee nicknames joined in.
5
Every create / edit / delete / drag triggers an API call
No localStorage for tasks — every mutation is an immediate POST, PATCH, or DELETE to Supabase. The board re-renders once the response comes back.

Key Files

supabase-client.js
Initialises the Supabase connection. Contains the project URL and anon key. No other file touches Supabase directly.
storage.js
All database queries live here. Maps DB snake_case columns to JS camelCase. The single swap point if the backend ever changes.
board.js
Task CRUD logic and card rendering. Calls storage.js for persistence. Never touches the DB directly.
ui.js
All event wiring — modals, nickname picker, filters, drag-and-drop. The app entry point.
drag-state.js
Tiny shared flag that prevents the detail modal from opening when a card is dropped after dragging.
vercel.json
Tells Vercel to serve the taskboard/ folder as a static site and sets CSP security headers.

Why There Is No Backend Server

Traditional apps have three layers: frontend → backend API server → database. This app skips the middle layer entirely.


Supabase's PostgREST engine automatically generates a full REST API from the database schema. The users and tasks tables are instantly accessible as HTTP endpoints. Row Level Security (RLS) policies on the database control what the browser is allowed to read and write — so there is no need for a custom API server to enforce those rules.


This architecture is called serverless or BaaS (Backend as a Service). It is well-suited for small teams where the data model is simple and there is no need for complex server-side business logic.
